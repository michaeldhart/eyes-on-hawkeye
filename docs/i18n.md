# Spanish version (i18n)

*Moved out of `CLAUDE.md` (it was one bullet under Conventions) so the always-loaded file stays short. Read this whenever you write or change anything a visitor sees, since every record needs its Spanish twin. Text is unchanged.*

- **Spanish version** (everything below is why the plan looks like this). English lives at `/`, Spanish at `/es/`. The language is chosen automatically: an inline script in the head of every English page sends first-time visitors whose browser prefers Spanish (`navigator.languages`, first of es/en) to the same path under `/es/`, hash included; Spanish pages never redirect. GitHub Pages is static, so there is no server-side negotiation. The footer link (English/Español) is the one switcher; it saves the choice in `localStorage` (`hawkeye-lang`), which the About page discloses, and that choice beats the browser setting. `hreflang` alternates, per-language canonical and `og:locale`, a Spanish social card (`assets/og-card-es.png`, same script) and `sitemap.xml` are emitted.
  - **Mechanics:** `_plugins/i18n.rb` clones documents, people and every page marked `i18n: true` (document and people indexes, timeline, search, `timeline.json`, `search.json`) under `/es/` with `lang: es`; any front matter key ending `_es` replaces its English twin on the clone. Liquid filters: `t` (UI string from `_data/i18n/{en,es}.yml`, flat keys, `%1`/`%2` placeholders), `tx` (field with `_es` fallback, for items in loops), `loc` (adds `/es`), `fdate` (`long`/`short`, Spanish month names), `tag_t`, `en_quotes`. Prose pages (home, About, Contact) are hand-written twins in `es/`. JS reads `window.I18N`/`window.LANG`, which the default layout prints on pages with `scripts:`.
  - **What gets translated:** titles, summaries, `date_note`, roles and `role_source`, person-page notes (`note_es`), type labels (`label_es`), tags (`_data/i18n/tags_es.yml`), UI strings, prose pages. **Not translated:** PDFs and the OCR full text (they are the record, and a machine translation of noisy OCR would look more authoritative than it is). Spanish pages say the original is English. Search on `/es/` indexes Spanish titles and summaries plus the English full text, folds accents, and a hint tells people to search English terms too.
  - **Ingest flow:** whenever you write an English summary, entry or role, write the Spanish in the same step (front matter `title_es`, `summary_es`, `role_es`, `role_source_es`; `scripts/add_document.py` takes `--title-es`/`--summary-es`). `python3 scripts/check_i18n.py` fails the build (CI runs it) if any record, type, tag or UI key lacks Spanish. Overview changes go in both `index.md` and `es/index.md`. Claude writes the Spanish itself, no translation API.
  - **Spanish style:** US Spanish, neutral, formal (usted), sentence case for titles and headings (the Title Case rule is English-only), full month names (`26 de mayo de 2026`), `p. m.`, `$` amounts as in the source, units as written. Quotes from the records stay in English followed by a translation in parentheses: `“enthusiastic interest” (“interés entusiasta”)`; the first quote is marked `lang="en"` automatically. Names, organizations and email subjects stay as written. Spanish forces gender on role nouns, so follow the pronouns the English text already uses (mayor = alcalde, City Attorney = abogado de la ciudad, finance director = directora de finanzas) and use neutral phrasing otherwise (`la representación legal del desarrollador`, `integrante del personal`). Never infer gender from a name.
  - **Review:** translations are AI-made and marked unreviewed on the site until a Spanish speaker checks them; set `es_reviewed: true` in that record's (or page's) front matter once checked and the note changes. check_i18n prints the count. The user and volunteers are reviewing.
